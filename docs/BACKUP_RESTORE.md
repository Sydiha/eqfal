# BACKUP_RESTORE — النسخ الاحتياطي والاستعادة (Foundation v1)

> **Object Storage (Task 6C-2B):** الأداة تغطي الآن `STORAGE_BACKEND=object` (انظر قسم «نسخ Object Storage» أدناه). الكود **غير مفعّل**: لم يُنشأ bucket ولم يُغيَّر أي إعداد في Replit/Staging/Production، ومفتاح `OBJECT_STORAGE_BACKUP_SUPPORT_CONFIRMED` يبقى قرار المالك بعد المراجعة. أول نسخة حقيقية من Object Storage لم تُجرَّب بعد (الاختبارات تستخدم عميلاً وهمياً).

أدوات يدوية في `tools/backup/`. **لا جدولة تلقائية ولا رفع خارجي** في هذه المرحلة (قرار المالك). كل أمر يُشغَّل يدوياً.

## الأهداف
| البند | القيمة |
|---|---|
| RPO (أقصى فقد بيانات مقبول) | 24 ساعة (نسخة يومية) |
| RTO (أقصى زمن للاستعادة) | 4 ساعات |
| الاحتفاظ | 7 يومية، 4 أسبوعية، 3 شهرية |

> RPO/RTO أهداف تصميمية. زمن الاستعادة الفعلي لم يُقَس إلا على بيانات تجريبية صغيرة؛ يجب قياسه على حجم بيانات حقيقي قبل الاعتماد عليه.

## ما الذي يُنسخ
1. قاعدة PostgreSQL بصيغة `pg_dump -Fc` (تشمل الشعارات المخزنة في `company_logos`).
2. مجلد المستندات (`DOCUMENT_STORAGE_DIR`) ومجلد ملفات استيراد البنك (`BANK_STORAGE_DIR`) كأرشيفين بصيغة EQFAL الخاصة (gzip) تُكتب وتُقرأ بكود المشروع نفسه، لا بـ `tar`.
3. `manifest.json`: SHA-256 لكل ملف (مشفّر وغير مشفّر) + ختم HMAC يكشف العبث بالـ manifest.

**لا يُنسخ:** متغيرات البيئة و`SESSION_SECRET` (تُحفظ بشكل منفصل وآمن). فقدان `SESSION_SECRET` يلغي الجلسات فقط.

## استراتيجية الاتساق (قاعدة ↔ ملفات)
1. تؤخذ لقطة القاعدة أولاً (`pg_dump` لقطة متسقة بذاتها).
2. تُؤرشف الملفات بعد انتهاء اللقطة.

**لماذا لا `tar`:** `tar` (GNU 1.35) يعيد الرمز 1 مع رسالة "file changed as we read it" أو "File removed before we read it" بعد أن يكون قد بثّ الملف المتغير فعلاً. كان الكود السابق يعدّ ذلك تحذيراً ويُنجح النسخة؛ هذا خطأ. الآن الأرشيف يُكتب بكود المشروع: كل ملف يُفحص (inode/size/mtime/ctime) قبل القراءة وبعدها، وأي تغيير أو حذف أو نمو أثناء القراءة يُلغي الأرشيف (`ConcurrentChangeError`) فلا تُصدَّق نسخة غير متسقة. تُعاد محاولة الأرشفة حتى 3 مرات (لقطة القاعدة تبقى قبلها فيبقى ترتيب الاتساق)، وإن استمر التغيير تفشل النسخة كاملة ويُحذف المجلد الجزئي. الملفات التي تُنشأ بعد بدء المسح لا تدخل الأرشيف ولا تُعدّ خطأ (يتيمة غير ضارة). الروابط الرمزية في التخزين تُرفض.

السبب: الملفات تُكتب مرة واحدة (`flag: 'wx'`) **قبل** تثبيت صفها في القاعدة (`document.service.ts`, `bank.router.ts`). لذلك كل صف داخل اللقطة له ملفه في الأرشيف. الملفات الأحدث من اللقطة تظهر "يتيمة" بلا صف وهي غير ضارة. إذا ظهر تحذير "file changed as we read it" فالمقصود ملف قيد الكتابة بلا صف في اللقطة، ويُسجَّل في `manifest.warnings`.

## التشفير
- AES-256-GCM مع مفتاح مشتق من عبارة المرور بـ scrypt؛ الترويسة مصادَق عليها (AAD)، والعبث بأي بايت يُفشل فك التشفير.
- لا يُكتب أي ملف غير مشفّر على القرص: المخرجات تُشفَّر أثناء التدفق (stream).
- العبارة: `BACKUP_PASSPHRASE_FILE` (ملف بصلاحية `600`، يرفض الأمر غير ذلك) أو `BACKUP_PASSPHRASE`، 16 حرفاً على الأقل. **احفظ العبارة خارج الخادم؛ بدونها لا استعادة.**
- مجلد النسخة بصلاحية `700` وملفاتها `600`. بيانات الاتصال بالقاعدة تُمرَّر عبر متغيرات `PG*` لا عبر وسائط الأمر.

## الأوامر
```
node tools/backup/cli.js backup  --out <dir>
node tools/backup/cli.js verify  --backup <dir>
node tools/backup/cli.js restore --backup <dir> --i-confirm-isolated-test-target
node tools/backup/cli.js prune   --root <dir> [--apply]
```
**نسخة:** `DATABASE_URL`, `DOCUMENT_STORAGE_DIR`, `BANK_STORAGE_DIR` + العبارة. يجب ألا يكون `--out` داخل مجلدات التخزين. اللقطة تُسمّى `eqfal-backup-YYYYMMDDTHHMMSSZ`. عند أي فشل يُحذف المجلد الجزئي. الأمر يطبع تنبيهاً بأن النسخة **أُنشئت ولم تُتحقق** بعد.

**تحقق (`verify`) = سلامة الملفات فقط:** يفحص ختم الـ manifest، SHA-256 للملفات المشفّرة وغير المشفّرة، توثيق التشفير، وأن بنية الأرشيفات سليمة وكل أسماء الملفات آمنة. **لا يثبت أن القاعدة أو الملفات قابلة للاستعادة.** مخرجاته تحمل `"restore_tested": false` و`"recovery_verified": false` دائماً.

**تنظيف (retention):** الافتراضي عرض الخطة فقط (dry-run)؛ `--apply` يحذف. يمسّ فقط مجلدات بالاسم `eqfal-backup-…` التي بداخلها `manifest.json`.

## مستويات الضمان (لا تخلط بينها)
| المستوى | ما يثبته | ما لا يثبته |
|---|---|---|
| 0 — `backup` | أن الملفات كُتبت | لا شيء عن الاستعادة |
| 1 — `verify` | الملفات سليمة وغير معبوث بها ومشفّرة بالعبارة الصحيحة | أن القاعدة تُستعاد، أو أن البيانات صحيحة |
| 2 — `restore` ناجح إلى هدف معزول (`recovery_verified: true`) | هذه النسخة بعينها استُعيدت إلى هدف معزول، وتطابقت الملفات والـ checksums والسجلات والقيود | الاستعادة الإنتاجية، وجود نسخة خارج الخادم، أو زمن RTO الحقيقي |

لا تُعدّ نسخة "قابلة للاستعادة" إلا بعد المستوى 2 لها (أو لنسخة حديثة مماثلة). يُنصح بإعادة التجربة دورياً وبعد أي تغيير في المخطط.

## الاستعادة: لبيئة اختبار معزولة فقط
متغيرات: `RESTORE_DATABASE_URL`, `RESTORE_DOCUMENT_DIR`, `RESTORE_BANK_DIR` (+ العبارة، و`RESTORE_TMP_DIR` اختياري للنسخ المؤقتة).

**إنشاء هدف قابل للاستعادة (مرة لكل اختبار):**
```
CREATE DATABASE eqfal_restore_drill1;
COMMENT ON DATABASE eqfal_restore_drill1 IS 'EQFAL_DISPOSABLE_RESTORE_TARGET';
```
الأداة **ترفض** ما لم يتحقق كل التالي (الأدلة مستقلة عن `DATABASE_URL`، فتعمل حتى لو لم يكن معرّفاً):
- اسم القاعدة يطابق `eqfal_restore_[a-z0-9_]+` **و**عليها التعليق `EQFAL_DISPOSABLE_RESTORE_TARGET` (علامة صريحة وُضعت عمداً؛ قاعدة حية لا تحملها).
- المضيف محلي (localhost أو socket).
- قاعدة الهدف فارغة تماماً (قاعدة حية أُعيدت تسميتها وعليها العلامة ترفض لأنها غير فارغة).
- الهدف ليس نفس قاعدة `DATABASE_URL` ولا `.env` ولا متغيرات `PG*`، **نصاً وأيضاً بهوية الخادم**: يُقارن `pg_postmaster_start_time` و`oid` القاعدة، فيُكشف التطابق مهما اختلف اسم المضيف (localhost / 127.0.0.1 / ::1 / socket).
- مجلدا الهدف مطلقان، فارغان (أو غير موجودين)، غير متداخلين، وليسا رابطاً رمزياً، ولا يتقاطعان مع مجلدات التخزين الحية أو مجلد النسخة.
- الراية `--i-confirm-isolated-test-target`.
- فحص سلامة الملفات يتم **قبل** لمس الهدف.

**التنفيذ:** تُفك كل قطعة وتُوثَّق كاملة إلى نسخة خاصة مؤقتة (صلاحية `700`) وتُحذف بعد الانتهاء. كل الخطوات اللاحقة تقرأ تلك النسخة الثابتة فقط، فلا فاصل زمني بين الفحص والاستخدام (TOCTOU)، ولا يمكن تجاهل فشل التوثيق المتأخر. ثم `pg_restore --single-transaction --exit-on-error` (كل شيء أو لا شيء)، ثم استخراج الأرشيفين، ثم التحقق.

**أمان الاستخراج:** أسماء المدخلات تُقبل فقط بالشكل `segment/segment` من الأحرف `A-Za-z0-9._-` (يُرفض `..` والمطلق والفراغ والمحارف الخاصة والتكرار وتعارض الملف/المجلد). الملفات تُنشأ بـ `O_EXCL|O_NOFOLLOW` وصلاحية `600` ولا تُكتب فوق شيء موجود ولا عبر رابط رمزي. يُتحقق من SHA-256 وحجم كل ملف وعدد المدخلات.

**التحقق بعد الاستعادة** (قراءة فقط): عدد الـ migrations وآخرها يطابق النسخة؛ كل `documents.storage_key` و`bank_import_batches.storage_key` له ملف بنفس SHA-256 (وحجم المستندات)؛ عدد الملفات اليتيمة؛ كل قيد مرحَّل متوازن؛ ميزان المراجعة لكل شركة متوازن؛ لا قيد مرحَّل بلا بنود. النتيجة: `restore_verification: passed|FAILED` و`recovery_verified: true|false`؛ الفشل يعيد رمز خروج `2`. عند أي فشل أثناء الاستعادة احذف قاعدة الاختبار وأفرغ المجلدين قبل إعادة المحاولة.

> استعادة إنتاجية حقيقية (فوق قاعدة حية) **خارج نطاق هذه الأداة** عمداً، وتحتاج إجراءً مكتوباً وموافقة صريحة من المالك.

## إجراء الكوارث (VPS واحد) — ملخص
1. جهّز خادماً/قاعدة جديدة فارغة بنفس إصدار PostgreSQL الرئيسي.
2. انسخ مجلد النسخة والعبارة إلى الخادم الجديد.
3. شغّل `verify` ثم `restore` إلى قاعدة فارغة، وراجع تقرير التحقق.
4. اضبط متغيرات البيئة (`DATABASE_URL`, `SESSION_SECRET`, مسارات التخزين) ثم شغّل التطبيق؛ تُطبَّق أي migrations ناقصة تلقائياً عند الإقلاع.

## نقاط لم تُحسم (تحتاج قراراً لاحقاً)
- **النسخ خارج الخادم:** هذه الأداة لا ترفع شيئاً. نسخة على نفس القرص لا تحمي من فقدان الخادم؛ انسخ مجلد النسخة يدوياً إلى جهاز/تخزين خارجي.
- **الجدولة:** غير مفعّلة (cron أو غيره) بانتظار موافقة.
- **نسخة قبل كل Migration:** يُنصح بتشغيل `backup` يدوياً قبل أي نشر فيه Migration.
- **حجم البيانات:** الأرشفة تمرّ على كامل المجلدات في كل نسخة (لا تزايدية).
- الاستعادة تحتاج `pg_dump`/`pg_restore` من نفس الإصدار الرئيسي لـ PostgreSQL. لم يعد `tar` مطلوباً.
- النسخة المؤقتة المفكوكة أثناء الاستعادة تُكتب في `RESTORE_TMP_DIR` (أو tmp) بصلاحية 700 وبحجم النسخة غير المشفّرة؛ تأكد من المساحة، ولا تستعمل بيانات حقيقية في بيئة غير موثوقة.

## نسخ Object Storage (Task 6C-2B)
عند `STORAGE_BACKEND=object` يعمل `backup` هكذا:
1. يلزم `OBJECT_STORAGE_BUCKET_ID` صريحاً (لا يُستخدم الـ bucket الافتراضي أبداً). قيمة `STORAGE_BACKEND` غير المعروفة، أو `local` على نشر Replit Production، يُرفض (لا نسخة فارغة صامتة).
2. لقطة واحدة متسقة: `pg_export_snapshot()` داخل معاملة `REPEATABLE READ`؛ `pg_dump --snapshot` وقراءة قائمة الملفات المرجعية (`documents.storage_key/sha256/size_bytes` و`bank_import_batches.storage_key/file_sha256`) من اللقطة نفسها. فلا تختلف قائمة الملفات عن القاعدة المنسوخة حتى لو رُفعت ملفات أثناء النسخ.
3. كل ملف مرجعي يُنزَّل (قراءة فقط: لا رفع ولا حذف ولا list) ويُقارن بـ SHA-256 (وبالحجم للمستندات) المسجل في القاعدة، ثم يُكتب مباشرة في الأرشيف المشفّر (لا ملف غير مشفّر على القرص).
4. **يفشل النسخ كاملاً** (ولا يبقى مجلد نسخة جزئي) عند: ملف مفقود ("No such object")، عدم تطابق SHA-256 أو الحجم، مفتاح تخزين غير آمن، أو أي خطأ خدمة/شبكة/صلاحيات (يُبلَّغ كخطأ خدمة لا كملف مفقود).
5. الملفات في الـ bucket غير المشار إليها من القاعدة (يتيمة) لا تُنسخ.

**التوافق:** صيغة الأرشيف (`EQFALAR1`) وأسماء الملفات (`documents.archive.gz.enc`, `bank-imports.archive.gz.enc`) وصيغة الـ manifest (`format: 2`) لم تتغير؛ أُضيف حقل `storage` (`backend`, `environment_label`, `referenced_files`) فقط. النسخ القديمة بلا الحقل تُعامل كـ local وتُتحقق وتُستعاد كما كانت، ونسخ `local` الجديدة لا تتغير. أرشيف Object Storage مطابق بايتاً ببايت لأرشيف مجلد يحوي الملفات نفسها (يغطيه اختبار).

**الاستعادة:** تبقى دائماً إلى بيئة معزولة (قاعدة `eqfal_restore_*` موسومة + مجلدات محلية فارغة خارج مجلدات التخزين الحية). أمر `restore` **لا يتصل بـ Object Storage إطلاقاً** ولا يكتب فيه، فلا يمكن أن يستعيد إلى تخزين الإنتاج. بعد الاستعادة تُفحص الملفات المستعادة (وجود، SHA-256، حجم) مقابل الصفوف المستعادة بالفاحص نفسه المستخدم لنسخ local.

متغيرات إضافية لـ `backup`: `STORAGE_BACKEND=object`, `OBJECT_STORAGE_BUCKET_ID`. مجلدا `DOCUMENT_STORAGE_DIR`/`BANK_STORAGE_DIR` يُتجاهلان في هذا الوضع. البادئة داخل الـ bucket (`prod/` أو `nonprod/` حسب `NODE_ENV`/Replit) تطابق `storage.factory.ts` (يتحقق منها اختبار).

**لم يُتحقق منه:** سلوك `@replit/object-storage` الفعلي على Replit (صيغة رسالة 404، الحدود، الأداء/زمن نسخ ملفات كثيرة أو كبيرة: كل ملف يُحمَّل كاملاً في الذاكرة ويُنزَّل تسلسلياً). على المالك تجربة أول نسخة حقيقية بعد تفعيل Object Storage، ثم اختبار استعادة معزولة، قبل ضبط `OBJECT_STORAGE_BACKUP_SUPPORT_CONFIRMED`.
