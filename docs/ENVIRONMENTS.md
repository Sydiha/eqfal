# ENVIRONMENTS

## الهدف
فصل Staging وProduction بطريقة صحيحة وآمنة وبأقل تكلفة ممكنة، دون نشر Production في مرحلة التأسيس الحالية.

## Staging
الاستخدام: التطوير، الاختبارات، Migrations، والتحقق قبل أي انتقال للإنتاج.

الضوابط:
- قاعدة بيانات مستقلة عن Production.
- أسرار مستقلة.
- ملفات/Storage مستقلة عند إضافة التخزين لاحقًا.
- بيانات تجريبية أو بيانات منقحة فقط.
- يمكن أن تكون البيئة غير دائمة التشغيل إذا كان ذلك يخفض التكلفة ولا يعيق الاختبار.

## Production
الاستخدام: البيانات الحقيقية فقط بعد الوصول إلى بوابة Production readiness وموافقة صاحب المشروع.

الضوابط:
- لا تُنشأ/تُنشر كبيئة تشغيل فعلية في هذه المرحلة.
- قاعدة بيانات وأسرار وStorage مستقلة عن Staging.
- أي نشر أو Migration يحتاج موافقة صريحة بعد نجاح Staging.
- لا استخدام لبيانات Production في Staging بشكل خام.

## تدفق التغيير
`feature branch → review/tests → PR → main → Staging validation → explicit approval → Production`

وجود Merge في `main` لا يعني تلقائيًا السماح بالنشر إلى Production.

## الإعدادات
يُخطط لاستخدام Environment Variables فقط، بأسماء عامة وغير مرتبطة بـReplit في منطق الأعمال. القيم الفعلية والأسرار لا تُحفظ في Git.

أمثلة فئات الإعدادات المستقبلية:
- `APP_ENV`
- `DATABASE_URL`
- Auth/session secrets
- Storage configuration
- Logging level

هذه أسماء تصميمية فقط؛ لا تُنشأ أسرار أو موارد الآن.

## مبدأ التكلفة
الفصل لا يعني شراء خادمين مدفوعين دائمين. نفضّل أقل شكل تشغيل يحقق:
1. عزل البيانات والأسرار.
2. إمكانية اختبار Migrations والتغييرات قبل Production.
3. عدم إضافة تكلفة تشغيلية دائمة دون حاجة مثبتة.

## قابلية النقل
يجب ألا تعتمد تعريفات البيئات على Replit حصريًا. عند النقل إلى سيرفر خاص، يكفي إعادة توفير متغيرات البيئة وقاعدة PostgreSQL والخدمات القابلة للاستبدال دون تعديل منطق الأعمال.
