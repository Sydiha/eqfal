# سياسة الصلاحيات — المرحلة الأولى

## الهدف والنطاق

تضيف هذه المرحلة سياسة صلاحيات مركزية ومُرقّمة الإصدارات، مع إبقاء جميع الصلاحيات الحالية كما هي. لا تُفعّل المرحلة الأولى الصلاحيات المستهدفة ولا تغيّر أي عضوية أو سجل `role_capabilities`.

| الدور | سياسة الإصدار المستهدف |
|---|---|
| System Administrator | جميع الصلاحيات المسجّلة في كل شركة نشطة، دون اشتراط عضوية. تظل قيود سلامة العمليات وفصل واجبات الرواتب قائمة. |
| Company Manager | جميع وظائف الشركة، مع بقاء صلاحيات إدارة الوصول الحالية فقط؛ لا تضاف صلاحيات `access.*` أو إنشاء شركة/تغيير حالة الشركة عبر ملف الدور. |
| Finance Manager | جميع صلاحيات المجالات المالية والمحاسبية المُعرّفة مركزيًا، بما فيها الرواتب، دون صلاحيات `access.*` أو إنشاء شركة. |
| Accountant | صلاحيات صريحة محدودة وقابلة للتهيئة؛ السياسة لا تضيف صلاحيات تلقائيًا. |
| أدوار أخرى | صلاحيات صريحة مخصصة ومقيّدة بنطاق الشركة وسقف المانح. |

يبقى System Administrator صفة عامة منفصلة عن عضوية الشركة. ويظل Full Access دورًا شاملًا داخل شركته فقط، مع استثناءاته الحساسة الحالية، ومنها الحاجة إلى منح صريح لاعتماد الرواتب. لا يتحول Company Manager إلى Full Access ولا يستطيع ملف السياسة منحه صلاحية `access.full_access.grant`.

## حالة الإطلاق

- تضيف قاعدة البيانات `authorization_policy_key` و`authorization_policy_version` للأدوار، و`system_admin_policy_version` للمستخدمين ذوي System Administrator.
- كل الإصدارات الافتراضية هي `0`. ترحيل 122 يعرّف الأدوار القياسية فقط ولا يضيف صلاحيات أو يغير العضويات.
- الأدوار القياسية الجديدة تُنشأ بمفتاح السياسة وإصدار `0`. لا يحصل المستخدم الجديد أو الشركة الجديدة على توسعة صلاحيات قبل التفعيل.
- عند الإصدار `0` يستمر الحل المركزي باستخدام الصلاحيات المخزنة الحالية. لا تظهر صلاحيات الإصدار المستهدف في الواجهة كأنها فعّالة.
- المحاسب يظل قابلاً للتهيئة حتى عند وسمه بالإصدار المستهدف؛ لا تُقفل منحُه الصريحة.

## التفعيل والتراجع — إجراء لاحق بموافقة منفصلة

1. الحصول على قاعدة قراءة فقط أو لقطة معتمدة، وإصدار تقرير فعلي للشركات والأدوار والعضويات والمستخدمين والصلاحيات الحساسة التي ستضاف. التقرير الحالي إسقاط برمجي فقط.
2. الحصول على موافقة مالك صريحة تحدد الشركة/الأدوار أو المستخدمين المستهدفين وتقبل أثر التوسعة.
3. في تغيير لاحق معتمد، تحديث `authorization_policy_version` للأدوار المحددة إلى `1` و/أو `system_admin_policy_version` للمستخدمين المحددين إلى `1` داخل معاملة مدققة. تحديث إصدار دور واحد يؤثر في كل عضوياته؛ يجب توثيق تلك القائمة قبل التنفيذ.
4. لا تُعدّل `role_capabilities` أثناء التفعيل. يسجل التدقيق الإصدار السابق والجديد والفاعل والهدف ونطاق الشركة.
5. للتراجع، إعادة الإصدار المحدد إلى `0` وتسجيل حدث تدقيق مقابل. تعود الصلاحيات الفعلية إلى الصفوف الصريحة المحفوظة؛ لا يلزم حذف صلاحيات أو عضويات.

لا تنفذ هذه الوثيقة أو migration 122 أي تفعيل. تظل مراجعة الأثر الفعلي وموافقة المالك شرطًا قبل أي تغيير إصدار إلى `1`.

## سلامة وأمن مستمرّان

- تظل حواجز الخادم، نطاق الشركة النشطة، وسقف منح الصلاحيات هي مصدر التفويض.
- لا تُنسخ طبقة السياسة المفعّلة تلقائيًا عند نسخ دور؛ تُنسخ المنح الصريحة المخزنة فقط. لا تُنسخ صلاحيات `access.*`، ولا يمكن إسناد دور من شركة أخرى إلى عضوية محلية.
- يظل Full Access خارج ملفات السياسات، وتظل قيود اعتماد الرواتب وترحيلها دون تغيير.
- أُعدّ الإسقاط البرمجي في [تقرير أثر المرحلة الأولى](PHASE_1_IMPACT_PROJECTION.md). **تقرير أثر الشركات والمستخدمين الحقيقيين: معلّق** حتى تتوفر قاعدة قراءة فقط أو لقطة معتمدة.
